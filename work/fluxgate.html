OpenFluxGate

서버가 늘어도 전체 허용량을 유지하도록 동시 요청의 토큰 확인·차감을 Lua 스크립트 하나로 묶어 Redis에서 원자적으로 실행했습니다. 규칙 변경은 Redis Pub/Sub으로 알려 각 앱이 감지하고 캐시를 갱신하게 했습니다. 제한 엔진과 Spring Boot 스타터를 Maven Central에 배포하고, 규칙을 관리하는 FluxGate Studio와 문서 포털을 별도로 개발했습니다.

왜 만들었나

요청이 몰릴 때 공용 자원을 보호하려면 서버가 늘어나도 전체 허용량은 유지돼야 합니다. 서버별로 요청 수를 집계하면 인스턴스 수에 따라 허용량도 증가할 수 있습니다. 여러 인스턴스가 같은 제한 상태를 공유하고, 서비스마다 제한 로직을 다시 구현하지 않도록 개인 오픈소스로 개발했습니다.

판단은 Redis 안에서 한 번에

남은 토큰을 확인하는 것과 차감하는 것이 분리되어 있으면, 동시에 들어온 요청이 같은 잔여량을 보고 함께 통과할 수 있습니다. 확인과 차감을 Lua 스크립트 하나로 묶어 Redis 안에서 원자적으로 실행합니다. 토큰 보충 시각은 Redis TIME을 사용해 애플리케이션 인스턴스 간 시계 차이의 영향을 줄였습니다.

스크립트는 EVALSHA에 KEYS·ARGV를 전달해 실행하고 NOSCRIPT 시 대체 경로를 둡니다. 스크립트 본문 반복 전송은 줄이지만 매 요청의 Redis 실행은 남습니다. 원자성의 대가로 해당 Redis 키·슬롯에 판단이 모이므로 핫키와 Redis 가용성은 별도로 고려해야 합니다.

무엇을 같은 대상으로 볼 것인가

제한 알고리즘보다 먼저 정해야 했던 건 "누구를 같은 대상으로 셀 것인가"였습니다. IP, 사용자 ID, API 키 중 하나로 제한할 수도 있고, IP와 사용자를 합친 복합 키로 더 잘게 나눌 수도 있게 했습니다. 초 · 분 · 시간 단위 제한을 함께 거는 멀티 밴드 규칙과, 즉시 거절하는 대신 토큰 보충을 기다리는 정책도 넣었습니다.

앱의 직접 연동과 HTTP 호출을 함께 지원

Spring Boot 애플리케이션의 Filter가 요청을 받아 RateLimitHandler에 판단을 위임합니다. 앱이 Redis를 직접 사용하는 Direct Redis 방식과 별도 Rate Limit Service를 HTTP API로 호출하는 방식을 제공했습니다. HTTP 경로에서도 실제 토큰 버킷 판단은 서비스 뒤의 Redis에서 처리합니다.

규칙 관리와 요청 처리를 분리

FluxGate Studio는 Next.js UI와 Spring Boot Admin API로 구성했습니다. Admin API는 Keycloak 기반 인증을 사용하고, 규칙 생성·수정·활성화와 규칙 현황을 제공합니다. 규칙은 MongoDB에 저장하며 MongoDB 어댑터를 설정한 앱이 읽습니다. HTTP 샘플은 별도의 Redis 규칙 저장소를 사용합니다.

규칙 변경은 Redis Pub/Sub으로 알리고 앱의 캐시를 무효화·재조회합니다. 현재 LTS 구현은 주기 조회도 두어 알림 누락을 보완합니다. 요청 차감의 Lua 원자성과 규칙 변경 알림은 별도 역할이며, Studio는 규칙 관리, Micrometer는 요청 처리 관측을 담당합니다.

Spring Boot 2.7과 3.x 스타터를 각각 제공하고 Maven Central에 배포했습니다. 적용 예제와 Docusaurus 문서 포털을 함께 관리합니다.

현재 LTS에서 다루는 원자성과 재시도 경계

현재 LTS 소스에서는 멀티 밴드의 조건을 모두 검사한 뒤 차감합니다. 여러 키가 같은 Redis 슬롯에 있을 때의 원자 처리와, 다른 슬롯에 걸친 실패 뒤 보상 환급은 구분합니다. 슬롯을 넘는 환급 전체는 원자적이지 않습니다.

실행 여부가 불명확한 차감은 자동 재시도를 제한해 이중 차감 위험을 다룹니다. 공개 배포본 0.3.7 이후 LTS 개발에서 추가한 개선입니다.

지금 상태

제한 엔진·Spring Boot 스타터를 Maven Central의 io.github.openfluxgate로 v0.3.7 공개 배포했습니다. 사내 POC와 팀 코드 리뷰를 진행하고 있으며, 실무 서비스 운영 이력과는 구분한 개인 프로젝트입니다.
