지마켓삼성카드 첫 적용

외부 파트너 제휴 연동 플랫폼

동의 한 항목의 실패가 완료된 인증을 되돌리지 않도록 트랜잭션을 나누고, 동시 도착하는 배치의 생성 경합과 누적 갱신을 따로 처리했습니다. 삼성카드 첫 연동의 구조 결정·구현·운영을 맡아 쿠폰 실패 건의 주기 재처리와 운영 관리자까지 연결했습니다.

어떤 상황이었나

카드사 같은 외부 제휴사와 회원 데이터를 주고받는 표준 채널이 없었습니다. 제휴가 하나 생길 때마다 연동 방식을 처음부터 다시 설계해야 했고, 이번에는 첫 제휴사를 붙이면서 다음 제휴사도 같은 구조로 붙일 수 있게 만드는 것이 목표였습니다.

까다로운 점은 동의가 한 곳에서 나오지 않는다는 것이었습니다. 지마켓 앱의 안내 화면에서도, 제휴사 앱에서도 동의가 발생합니다. 한 방향으로 API를 호출하는 것만으로는 두 시스템의 동의 상태가 맞지 않고, 외부 연동이 실패했다고 회원 탈퇴 같은 핵심 처리가 막혀서도 안 됐습니다. 2인 팀에서 구조를 제가 결정하고, 설계와 구현, 이후 운영까지 맡았습니다.

브라우저 인증·동의와 쿠폰 재처리는 별도 흐름

제휴 시작부터 인증 이후 동의까지는 브라우저에서 UUID를 만들고, Redis에 해당 키가 없을 때만 저장한 뒤 외부 금융사와 연동합니다. 외부 실패 시 키를 유지하고 오류를 MongoDB에 기록하며, 브라우저가 인증 상태를 조회해 재시도 안내를 받도록 했습니다. 금융사 상태 조회 API가 없어 외부 시스템의 중복 처리 정책에 의존하는 구간이 남았습니다. Redis 키의 중복 저장 방지만으로 외부 호출 전체의 정확히 한 번 실행을 보장하지는 않습니다.

이 UUID 흐름은 쿠폰 발급 과정이 아닙니다. 쿠폰 발급은 백엔드에서 수행하고, 실패 기록을 주기적으로 재처리합니다.

제휴 전용 진입 경로를 분리한 이유

제휴 API의 Gateway 경로를 분리하고, 특정 route를 통해 Nginx로 들어오도록 구성했습니다. 제휴 트래픽에 방화벽·보안 정책과 모니터링을 적용할 지점을 구분하기 위해서였습니다.

후속 업체도 같은 진입 구조를 사용하도록 설계했습니다. 업체별 경로와 정책을 추가하는 일은 Gateway에서, 동의와 배치의 업무 규칙은 애플리케이션에서 다루도록 책임을 나눴습니다.

인증 완료와 동의 저장의 실패를 분리

본인 인증이 끝난 뒤 동의를 저장하는 흐름은 두 트랜잭션으로 나누기로 결정했습니다. 인증 성공 이벤트를 커밋 이후에 받아서, 동의와 동의 이력은 새 트랜잭션으로 저장합니다. 동의 저장이 실패해도 이미 끝난 인증을 되돌리지 않고, 두 실패를 따로 다루기 위해서였습니다. 같은 항목에 이미 동의가 있으면 성공으로 분류해서, 같은 요청이 두 번 와도 결과가 달라지지 않게 했습니다.

여러 동의 항목은 항목별 새 트랜잭션으로 처리했습니다. 한 항목이 실패해도 완료된 인증과 다른 항목의 커밋은 보존합니다. 대신 일부만 성공한 상태를 이력과 함께 운영해야 합니다. 커밋 이후 이벤트 처리 자체가 영속적인 전달이나 모든 실패의 복구까지 보장하는 것은 아닙니다.

묶음으로 오는 배치

일배치는 하루치 데이터가 여러 묶음으로 나뉘어 도착합니다. 첫 묶음들이 동시에 집계 행을 만들면 유니크 충돌이 날 수 있어, 생성만 별도 트랜잭션으로 분리했습니다. 충돌한 요청은 기존 행을 다시 읽게 해 생성 실패가 주 트랜잭션을 실패 상태로 만들지 않도록 했습니다. 같은 배치의 중복 검사와 누적 갱신은 비관적 행 잠금 안에서 수행해 덮어쓰기를 막았고, 그 대신 같은 배치 요청의 락 대기를 감수했습니다.

같은 배치의 동일 묶음 번호를 다시 받으면 누적하지 않고 정상 종료합니다. 수신 묶음 수가 전체 묶음 수 이상이면 번호 누락과 항목 건수를 검사해 완료 또는 불일치 상태를 기록합니다. 도착 순서가 바뀌어도 가장 큰 묶음 번호만 보고 완료로 처리하지 않도록 했습니다.

외부 호출과 파일 오류를 운영자가 확인하도록

리워드는 회원·제휴 경로, 인증 성공, 유효한 마케팅 동의를 확인한 뒤 외부 응모 API를 호출합니다. 실패한 호출은 MongoDB에 기록하고, 제휴사·회원·이벤트 조합의 유니크 인덱스로 실패 기록 중복을 막았습니다. 운영자는 관리자 화면에서 실패 대상을 조회할 수 있습니다.

삼성카드 제휴의 쿠폰 발급 실패 건은 주기적으로 재처리하는 절차를 실제 운영했습니다. 재처리된 실패 건은 이후 쿠폰 발급으로 이어졌고, 사용자가 이벤트 쿠폰 혜택을 받을 수 있었습니다.

월배치는 Spring Batch chunk 처리로 파일을 적재하는데, 레코드 검증이나 복호화 오류는 제한된 수까지 건너뛰고 재암호화 같은 시스템 오류는 작업 실패로 남겼습니다. 한 행의 데이터 문제로 전체 파일을 멈추지는 않되, 시스템 문제는 조용히 넘기지 않기 위해서입니다.

만들고 끝이 아니라 운영까지

동의 규모는 일 평균 약 500명입니다. 운영팀이 개별 문의와 배치 결과를 확인할 수 있도록 제휴사 관리, 동의 조회, 배치 모니터링, 리워드 실패 목록을 Next.js 관리자 화면으로 만들었습니다.

제휴 처리 담당자가 관리자에서 동의를 철회하도록 구현했습니다. 동의 등록은 별도 금융사 페이지의 인증을 거쳐야 하므로 관리자에서 제공하지 않았으며, 회원 탈회와 동의 철회도 별도로 다뤘습니다.

연동 이력과 개인정보 조회 감사 기록은 분리하고 목적에 따라 보관 기간을 달리했습니다.
